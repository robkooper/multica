# AGENTS.md

Multica squad configuration as code. `story.md` is the owner's Medium article this setup started from, published at https://medium.com/@rob.kooper/running-a-coding-agent-squad-with-multica-on-your-own-vm-8655aba5d3a5. Medium often blocks automated fetches, so do not rely on reading the URL: the user downloads the article and saves it as `story.md` in the repo root (it is gitignored, so it is missing in a fresh clone; ask for it if you need it). Read it for background when present, but the files here are the source of truth and have moved past it:

- One Multica workspace per GitHub repo (exactly one repo under Settings → Code, found with `multica repo list`), not one workspace with a project per repo. Workspaces: `lumen` (ncsa/lumen), `taloscluster` (ncsa/taloscluster), `barn` (AIFARMS/barn, issue prefix BARN), and `ncsa`, the old all-in-one workspace that still has a project per repo and the old "GitHub Issue Sync Lumen" autopilot.
- One Multica project per GitHub milestone. The link is the last line of the project description: `GitHub milestone: <milestone html_url>`, or `GitHub milestone: none` for the "No milestone" project. Prompts and autopilots rely on this marker; do not change it in one place only.
- The `github-milestone` skill (used by Architect and Builder) holds the milestone rules: the issue's open milestone, otherwise the current one (earliest due date, else lowest version). Sub-issues go in that milestone's project. Milestones contain issues, never PRs: a PR gets no milestone and reaches it through the parent's GitHub issue (`Part of #N`, `Fixes #N` on the last PR of the stack), and a parent with `gh_number` is moved on GitHub too so the sync does not move it back. The Lead (squad rule 1) uses the skill to link every new top-level issue to GitHub before planning: it reuses an existing GitHub issue with the exact same title or creates one, on the project's milestone, and sets `gh_number` and `gh_updated_at` so the sync adopts it instead of creating a duplicate. Keep the skill, the sync autopilot and the PR Comment autopilot in agreement.
- Synced issues carry metadata `gh_number` (number) and `gh_updated_at`. PRs linked to an issue on GitHub (`closedByPullRequestsReferences`) get one `/note Linked pull request on GitHub: [#N title](url)` on the Multica issue; Multica itself only links a PR whose title, branch or body closing keyword names the Multica key, and has no API to add a link. Closing an issue on GitHub closes it in Multica on the next sync, whatever its status (done, or cancelled when closed as not planned, which also cancels its open sub-issues without `gh_number`). Issues without `gh_number` (Architect sub-issues) are not synced but move with their parent.
- GitHub sub-issues are mirrored as Multica parent links by the sync autopilot. An issue with GitHub sub-issues is an epic: created unassigned, never planned or split (Lead rule 1, Architect). A sub-issue with `gh_number` is a GitHub epic child and a full issue of its own with its own milestone; only sub-issues without `gh_number` follow the Architect/Builder sub-issue flow. The GitHub Issue Sync autopilot is the only sync; there is no separate resync script.
- Extra agents not in the article: Plan Checker and Senior Reviewer (in the squad), Monkey and Release Agent (standalone). The Plan Checker sends gaps back at most twice (counted since the human's last comment, then `Plan check: needs human`) and never re-raises the plan's own open questions. The Builder uses `gh stack` for stacked PRs.

## Pitfalls

- `apply.sh` matches agents, squads and autopilots by name: a rename creates a new one and leaves the old one running. New autopilots are created paused.
- `dump.sh` overwrites the files here with what is in the workspace. Prompt edits made in the Multica UI are lost on the next `apply.sh` unless dumped first.
- Autopilots have `project: null` and must stay repo-agnostic so the same files work in every workspace.
- The Lead (a small model) routes on the exact hand-off lines, listed at the top of the squad rules (`Ready for review|No change: <sha>`, `Verdict: approve|changes requested <sha>`, `Senior verdict: approve|changes requested <sha>`, `Plan check: approve|changes requested|needs human`, `Sub-issues created: …`). Change a line in an agent prompt and the squad rules together.
- The Lead runs every squad issue: it is the only agent that starts other agents. Agents never mention each other (they still mention the human when escalating); each ends with a hand-off line and the Lead routes on it (Planner `## Plan` → Plan Checker → human → Architect `Sub-issues created: …` → per sub-issue: Builder `Ready for review: <sha>` → Reviewer A and B in parallel, routed once both posted `Verdict: … <sha>` → Senior `Senior verdict: … <sha>` → next sub-issue). Architect sub-issues (title `<n>/<total>`, no `gh_number`) are assigned to the Delivery squad, not the Builder, because the Lead is only woken by comments on issues assigned to the squad. Approvals are per commit: any new commit goes back to both reviewers, and the Senior Reviewer refuses a head that both have not approved. A comment that mentions anyone, the human included, is delivered only to those mentioned, so the Lead is not woken by it: a hand-off line must sit in a comment with no mentions (the Senior Reviewer posts its summary for the human as a second comment; when it did not, LUM-303's second sub-issue never started). Do not reintroduce agent-to-agent mentions: they start agents twice and wake the Opus Builder for nothing (before this change about half its runs only acknowledged an approval).
- Every comment on a squad issue wakes the Lead, also in backlog (the human adding detail, or the sync copying GitHub comments). The squad rules make backlog mean "not started": the Lead does nothing on a backlog issue until the human moves it out of backlog or asks it to start (LUM-355 was started by a comment added right after creating it).
- `multica` CLI facts that are easy to get wrong:
  - `issue create` has no metadata flag; use `multica issue metadata set <id> --key K --value V`.
  - `issue list --limit` max is 100; page with `--offset` until `has_more` is false.
  - Project statuses: planned, in_progress, paused, completed, cancelled. Issue statuses: backlog, todo, in_progress, in_review, done, blocked, cancelled. Backlog never starts a run.
  - `--description-file` / `--content-file` must be inside the current directory.
  - `issue update --no-start` avoids waking the assignee. Editing a comment re-triggers every agent it mentions.
- All agents use the owner's GitHub account (one token on the VM), so anything they post on GitHub appears as the owner. Reviews stay in Multica only: Reviewer A and Reviewer B are read-only on GitHub, the Senior Reviewer only posts one "**How to test**" comment per PR on approval (updated in place, skipped by the PR Comment autopilot), the Builder only pushes branches and writes PR bodies, and the Lead only creates issues and sets milestones. Do not add any other `gh pr comment`, and no `gh pr review`, in a prompt.
- CI: the Builder waits for green checks before every hand-off and re-runs an unrelated failure once. The PR Comment autopilot (every 15 minutes) reports failing checks on our own open PRs (never on PRs that are not ours) to the sub-issue, once per head commit, deduplicated by the line `CI failed on <short sha>`, and merge conflicts once per head commit, only on our own PRs (`Merge conflict on <head> against <base>@<sha>`, deduplicated on the head alone, so main moving on does not repeat it); it finds the sub-issue from the branch name, not the PR author, since all agents push as the owner. It runs as the Lead, and the Lead never reacts to its own comments, so the autopilot mentions the Builder in those reports itself (without that, the LUM-333 conflict sat unnoticed).
- Mentions must be links: `[@Name](mention://member/<user_id>)` for a human, `[@Name](mention://agent/<id>)` for an agent. A plain `@name` notifies nobody. Every agent that escalates sets the issue to blocked and mentions the human with a link (the "Mentioning the human" block in Plan Checker, Builder, Senior Reviewer, Monkey and Release Agent, and squad rule 0).
- The agents' VM has no Docker, PostgreSQL or Redis: tests that need them are skipped locally and only run in GitHub Actions. The Senior Reviewer never counts a skipped test as passed; it confirms them in the CI logs, and anything covered by neither goes to the human as "Needs your testing" with exact commands (in the Multica review, and in the PR's "**How to test**" comment when it is about testing that PR).
- Multica never retries a failed run (for example a Claude usage limit). It only posts a "delegated task ended in a final failure" notice and wakes the agent that delegated the work, often the Architect, which runs on Claude and fails on the same limit. So the Lead (on Lumen, not limited) gets a task.failed wakeup on every parent (squad rule 1) and every sub-issue (Architect step 5), and squad rule F reschedules the failed agent after the reset time. All other agents ignore those notices. Wakeups are per issue; cross-issue subscriptions do not exist.
- Monkey runs go on the current milestone (Daily Monkey prompt, Monkey step 1), and their findings are sub-issues in the same project, in backlog, assigned to the Delivery squad. Moving a finding to todo starts the squad on it as a new issue (rules 1 to 4, linked to GitHub by the Lead), not as an Architect sub-issue; the Lead tells them apart by title.
- Test runs: every agent that runs the suite (Builder, Reviewer A, Senior Reviewer, Monkey) runs it once per code change with the output in a log file (`> ../pytest.log 2>&1; echo "exit=$?"`), judges by the exit code and greps the log. Piping pytest through `tail`/`grep` hid the summary (it comes before the coverage report and warnings) and made the Builder rerun the 4-minute suite four times. Reviewer A takes the full-suite result from CI when CI is green on the head.
- A run with no output for 10 minutes is killed by the idle watchdog and its scratch directory is wiped. Long agent work (the Monkey) must run one short command per step and checkpoint on the issue (the Monkey keeps a "## Monkey progress" comment it resumes from), never one long script.
- Never commit or push unless asked.
